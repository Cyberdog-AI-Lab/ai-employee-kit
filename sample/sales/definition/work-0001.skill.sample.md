## 入力と実行時パラメータ

毎回input_path、start_date、end_dateを受け取る。期間は実在するYYYY-MM-DDで開始<=終了。未指定ならCSVから推測せず確認。CSV項目はsale_id,date,product,channel,quantity,unit_price_jpy。quantityは空欄か0以上の整数、unit_price_jpyは0以上の整数、dateは実在YYYY-MM-DD、sale_id/product/channelは必須文字列、channelは店頭かEC。

必須値が不足または不正で確認待ちになる場合は、[手順1](#skl-006)から[開始前の停止記録](#skl-010)へ接続する。質問を返す前に記録し、CSVから値を推測しない。

実行時に次の3値を依頼から受け取る。定義を配置した時点の値は未指定であり、下表は入力仕様である。

| 子要素キー | 値の仕様 | 不足/不正時 |
| --- | --- | --- |
| input_path | 必須のパス。W基準の相対パスも可。解決後がW/inputs/sales-fictional.csvと一致すること | 別資料を選ばず、今回使う入力を確認 |
| start_date | 実在するYYYY-MM-DD、開始日（含む） | 入力CSVから推測しない |
| end_date | 実在するYYYY-MM-DD、終了日（含む）、start_dateより前にしない | 開始日との前後を確認 |

日付の両端包含はSIM-003からの生成側の具体化であり、回答台帳の提案として追跡する。CSVの文字列は保存時に原文を保持し、元の値を書き換えない。整数形式は半角数字だけの `[0-9]+` として読み、負数・小数・空白・指数表記を推測変換しない。quantityの空文字だけを未確定とし、文字列の0は有効な既知値。値を丸めない。

入力の形式、必要項目、今回の期間・単位・対象を確認する。欠損・重複・矛盾が判断に影響し、処理方針が未定ならその結果を確定しない。不明として出力することが確認済みの手順で認められる場合は、その範囲を明示する。

## 手順・判断・停止条件

期間の選別より先にファイル全体の必須形式/ID重複を点検する。不正なら集計しない。妥当なら期間判定し、数量空欄を未確定、数量既知の行を単価×数量・整数円で集計する。商品別/日別/販売経路別の既知金額と数量を作る。

以下は実行時の手順であり、生成・配置ターンでは実行しない。ローカルPython3標準ライブラリ（csv / datetime / pathlib / hashlib / json / html / uuid等）だけを使う。補助スクリプトが必要なら当該runの記録下に新規保存し、期待値や固定集計結果を埋め込まない。

1. 業務依頼、3パラメータ、定義記録と直前run/停止recordを読む。先にrecordsの実パス・許可範囲・新規書込み可否を確認する。必須値が不足または不正なら開始前の停止として、SKL-010に従い新しい停止recordを保存してから少数の確認を返す。記録を書けない場合だけ同じ内容を会話に残す。この時点ではoutputsを作らず、集計開始前に止める。再開時は旧停止recordと解消した条件を参照する。今回の生成だけの許可を流用して業務を開始しない。
2. 3パラメータが揃い妥当で、必要な実権限を確認してから、旧停止recordとは別の衝突しないrun_id（UTC日時＋ランダム識別子）を作り、`records/<run_id>/` と `outputs/<run_id>/` を新規作成する。既存なら別IDを作る。全ファイルを排他的な新規作成で保存し、開始記録と終了/停止記録は別名にする。入力コピーと同一CSVの外部原本のSHA-256、手順版・実体のハッシュ、パラメータ、確認した実環境を開始記録へ残す。配置時ハッシュと違えば、入力版の相違として集計を止める。ハッシュを取れないときは未確認と理由を残す。
3. CSV全体を期間選別前に読む。UTF-8（BOMがあればutf-8-sig）と `newline=''`、`csv.reader(..., strict=True)` を使う。ヘッダーの6項目を重複なく確認し、各レコードの列数と全必須値を検査する。項目名で対応づけ、余分/不足列や壊れた構造はエラーにする。各読取り直前の `reader.line_num + 1` を開始物理行、読取り後の `reader.line_num` を終了物理行とする（ヘッダー1行目）。複数行フィールドでは範囲も残し、単なるレコード番号で代用しない。完全な空行や空白だけの必須文字列も見落とさず問題として記録する。
4. sale_id/product/channelの必須性、channelの店頭/EC、日付の書式と実在性、整数書式/非負を全行で点検する。sale_idの重複は最初の行を含む関連全行を報告する。空のquantityは形式エラーにしない。期間外の行も検査を省略しない。行単位で読み続けられるエラーは収集を続け、全入力の問題行を列挙する。CSV構造/デコードエラーで続行不能なら集計せず、判明した行・到達位置と未検査範囲を明記する。全行を検査したと偽らない。
5. 不正形式/重複が1つでもあれば金額・数量を集計しない。問題行の物理行番号、sale_id（取得できる場合）、項目、原値、理由と検査範囲を `records/<run_id>/validation-errors.json` に新規保存し、停止理由/再開条件を引き継ぐ。quantity空欄だけなら次へ進める。
6. 妥当な全データ行に一意の物理行識別と元値を保持し、`start_date <= date <= end_date` で分類する。期間外は `outside_period`、期間内quantity空欄は `pending_quantity`、期間内quantity既知は `accepted`。期間外の空欄も別の `quantity_missing` フラグで追えるようにする。分類は相互排他的にし、空欄行を0円に変換しない。
7. acceptedだけを `quantity * unit_price_jpy` の整数円で計算し、商品別・日別・販売経路別に数量と金額を加算する。未確定行の金額・数量はnullで表し、既知行が0件なら既知分合計0と採用0件を明示する。商品名等をコード、HTML、保存パスに使わない。未知の商品/日付/集計結果を固定値で補わない。
8. 全体の空欄行をsale_id/物理行/理由で別掲する。入力全体に1件でも空欄があれば、期間外の場合も「完全な総売上」と呼ばず、既知分・暫定集計と表示する。期間内未確定件数と全入力空欄件数は分ける。成果物と検証結果を新規保存し、自己検査後に原本/コピーのハッシュを再確認する。結果を店主役へ渡して人の検収待ちで止める。

分岐や閾値は確認された業務条件に従う。原本を保持し、手順にない重要な判断は創作せず確認する。

## 出力

ローカルHTML/JSON。3内訳、既知金額/数量、期間、全行分類、物理行番号/sale_id、検証結果を収録。HTMLは内蔵CSS/SVG棒グラフ、外部URL/CDNなし、元データの文字列はHTMLエスケープ。

`outputs/<run_id>/report.json` は最低限、run_id、手順版、入力パスとハッシュ、start_date/end_dateと両端包含、状態、既知分数量/金額、by_product/by_date/by_channel、全行のtrace、未確定一覧、検証結果、未解決、human_acceptance=falseを持つ。traceには元フィールド値、開始/終了物理行、sale_id、分類、quantity_missing、採用行の計算値を含める。数値はJSON数値、未確定はnullとし、未確定一覧には理由を含める。実際の値は入力と計算から作り、期待値ファイルは使わない。

`outputs/<run_id>/report.html` は同じ計算データから見出し・期間・既知分の数量/金額・3内訳の表と棒グラフ・全行追跡・未確定の注意・検証結果を作る。CSS/SVGは文書内に置き、外部URL/CDN、JavaScript、外部フォント、外部画像を使わない。棒の長さは計算値に比例させ、全値0ならゼロ表示とし0除算しない。JSON由来の文字列をHTMLへ直接埋め込まず、テキストと属性の双方で `html.escape(..., quote=True)` を使う。商品名等をURL/イベント属性/生のHTMLやCSSとして扱わない。JSONファイルは `json.dump` 等で正しくエンコードする。ローカルで開ける一式とし、この試験ではブラウザ操作は行わない。

成果物はEMP-004の指定先に保存し、根拠・除外条件・未確定箇所・確認待ちを読み取れる形にする。既存ファイルと衝突したら無確認で置換しない。

## 検証

既知合計と3内訳和/採用行金額和・数量和、全行分類の一意性/網羅性、原本SHA-256前後一致、HTMLの外部資源なし/文字列エスケープを確認し結果を記録する。見た目は検証の代わりにしない。

- 採用行金額の再計算和＝既知分金額＝by_product/by_date/by_channel各金額和。数量も同様に照合する。期間外/未確定が採用へ混入していないこと。
- 全入力データ行の一意識別がtraceに1回ずつあり、3分類件数の和がデータ行数に一致すること。ヘッダーとデータ行を区別する。空欄はnull/理由付きで、原値を保持していること。
- JSONを再読込みし、生成元データ/検証対象と照合する。HTMLの数値/表/グラフは同じデータから生成したことを確認し、HTML文字列のエスケープと外部資源不使用を静的点検する。見た目や整合式だけで業務上の正しさを保証しない。
- 外部原本とW入力コピーの開始/終了SHA-256が配置時ハッシュとも一致すること。変化/未確認なら自己検査成功にしない。入力は修復・復元しない。
- 失敗した検査は結果と影響を記録し、成功扱いしない。実行した検査、未実施の見た目確認、人間検収未了を分ける。

実施した検査と結果を記録し、実施していない検査を成功と報告しない。根拠と出力を照合し、重大な失敗を見栄えや速さで相殺しない。

## 失敗・中断・再開の引継ぎ

失敗/中断は入力ハッシュ、手順版、済/未処理、部分成果、停止理由、再開条件をrecordsの新規runへ残す。再開は直前記録を読み、新runで始め、既存成果物は上書きしない。

実行時必須値の確認待ちも「開始前の停止」とする。手順1で、質問を返す前に、許可済みの `W/records` と新規書込み可否を確認し、UTC日時＋ランダム識別子の新しい `stop_run_id` を使って `records/<stop_run_id>/stopped-before-start.json` を排他的に新規保存する。既存IDなら別IDにし、既存記録は置換しない。この時点では `outputs/` や `outputs/<stop_run_id>/` を作らず、CSV検証・集計・レポート生成を開始しない。保存できたことを確認してから不足値の質問を返す。

停止記録には `run_id`、UTC時刻、`status=stopped_before_start`、手順版と正本SkillのSHA-256、不足したパラメータ名（不正なら項目名・理由も）、確認済みの実行値、確認済み入力パス/実パス/SHA-256、保存先/新規書込みの確認結果、処理済/未処理、`partial_artifacts=[]`（業務の部分成果なし）、`outputs_created=false`、停止理由、再開条件、旧record参照（ある場合）、`human_acceptance=false` を残す。入力パスが未指定なら別資料や既定のCSVで補わない。パスが確認済みの指定入力だけをハッシュ照合に読み、取得できない項目はnullと「未確認」の状態・理由を記す。ハッシュ取得不可を理由に停止記録そのものを省略しない。

保存先を確認できない、または新規保存に失敗して記録を書けない場合だけ、同じ内容と保存不能の理由を会話に残す。保存したと偽らず、別の未許可先へ保存しない。値が補われたら、旧停止recordを読み、参照先・停止理由の解消・入力/定義版を確認して、手順2の別runを開始する。旧停止recordを開始記録に参照し、旧recordと既存成果物は保持する。外部原本と入力コピーの実行前後のハッシュ照合は従来どおり手順2/8とSKL-008で行う。

記録にはrun_id、時刻、手順版/ハッシュ、入力の実パス/ハッシュ、実行パラメータ、済/未処理段階、部分成果のパス/状態、エラー、停止理由、再開条件と旧run参照を含める。部分成果があっても完了扱いしない。書込みそのものができない場合は会話で同じ内容を報告し、記録できたと偽らない。再開は旧runの状態を読み、未決の解決と入力/定義版を確認して新しいrunを使う。検収待ちは停止理由の1つとして保持する。

実行した処理と未実行の処理、部分成果の場所・状態、止まった理由、必要な確認、再開条件を残す。再開前に既存成果物と入力の版を確認し、二重処理・無確認置換・無制限の再試行を避ける。
